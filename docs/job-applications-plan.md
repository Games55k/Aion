# 求职插件：投递记录实施方案

状态：待实现。本文是供开发 agent 执行的产品与技术方案，不代表已上线功能。

## 1. 目标

为 Aion 增加第二个独立内置模块「求职」，核心页面为「投递记录」。用户可以用类似表格的方式记录公司、岗位、投递日期、面试进度、投递链接和失败原因，并查看流程历史。

遵循 Aion 本地优先、纯原生的定位：数据存入现有 SQLite，使用 Lobe MyGo 构建界面，复用全局设置、备份与系统能力。投递记录独立于项目和任务，不要求创建项目。

## 2. 第一版范围

必须交付：

- 「项目 / 求职」模块切换及求职专属导航。
- 投递记录的新增、查看、编辑、软删除、恢复与彻底删除。
- 表格视图、搜索、筛选、排序及基础统计。
- 当前阶段、流程状态、结束结果与结束原因管理。
- 投递链接、投递渠道、通用备注及下次跟进日期。
- 阶段变更时间线、补录历史与备注。
- 自动保存、失败重试及切换页面时的草稿保护。
- 数据库升级、全量备份与旧备份恢复兼容。

后续再考虑：看板视图、自定义阶段、CSV 导入导出、系统提醒、简历附件、转化率分析、批量操作。第一版不实现通用表格引擎、自由添加列、公式、在线协作、第三方可执行插件加载或插件市场。

## 3. 导航与页面

### 3.1 模块入口

沿用现有模块注册机制，建议 ID 为 `job_applications`，名称为「求职」。顶部支持「项目 / 求职」切换；侧栏折叠时也必须能切换模块。

切入求职后显示以下固定视图，视图共用同一份数据，通过条件过滤：

| 入口 | 条件 |
|---|---|
| 全部投递 | 未删除的全部记录 |
| 进行中 | `lifecycle = active` |
| 已获 Offer | 当前阶段为 Offer，或历史上曾到达 Offer |
| 已结束 | `lifecycle = closed` |

已获 Offer 可以与进行中、已结束重叠。回收站与设置保持全局入口，回收站可按模块或条目类型筛选。

模块切换保留各自搜索、筛选和列表位置；切换前必须处理待保存草稿。不要仅修改 `activeModule` 而继续渲染项目页面。

### 3.2 表格页面

顶部提供新增投递、关键词搜索、阶段/结束结果/投递日期筛选及排序。关键词搜索公司与岗位，筛选条件之间取交集。默认按投递日期倒序，相同日期用稳定的次级排序。

默认列：公司、岗位、投递日期、阶段、状态/结果、下次跟进、链接。结束原因与备注在详情中完整展示，可在行内显示简短摘要，不因长文本无限撑高行高。

支持按投递日期与最近更新时间排序。窄窗口下优先保留公司、岗位和进度，其余列允许横向滚动或进入详情查看。数据量增加时使用分页或受控的行渲染，避免每帧查询数据库。

顶部显示总投递、进行中、已获 Offer 数量。第一版统计口径为所有未删除记录，不受当前搜索和筛选影响；列表单独显示当前匹配数。公司数不等于投递数，同一公司的不同投递逐条计数。

### 3.3 新增与详情

- 新增弹窗仅强制填写公司、岗位和投递日期；日期默认当天，阶段默认已投递。
- 公司和岗位去除首尾空白后不得为空；日期为本地日历日期，不因时区变化偏移。
- 表格支持行内修改阶段和下次跟进日期；完整编辑通过点击记录打开详情弹窗。
- 详情包含基本信息、流程信息、链接与备注、时间线，遵循现有 UI 的布局与主题规范。
- 同公司、同岗位已有进行中记录时提示可能重复，允许继续创建，不建立阻止重复投递的唯一约束。
- 同公司不同岗位、同岗位再次投递均允许创建独立记录。
- 链接可复制，打开通过 `frontend.Host.OpenURL`，仅允许有效的 HTTP/HTTPS 链接；打开失败应有反馈。
- 下次跟进日期第一版只用于显示和筛选扩展，不承诺系统通知。

## 4. 字段与流程语义

### 4.1 记录字段

| 字段 | 必填 | 说明 |
|---|---|---|
| 公司名称 | 是 | 文本 |
| 岗位名称 | 是 | 文本 |
| 投递日期 | 是 | `YYYY-MM-DD`，支持历史日期 |
| 当前阶段 | 是 | 固定枚举，默认已投递 |
| 流程状态 | 是 | 进行中、已结束 |
| 结束结果 | 已结束时必填 | 未通过、接受 Offer、拒绝 Offer、主动放弃、岗位取消、其他 |
| 结束原因 | 否 | 多行文本，记录失败、放弃或其他结束原因 |
| 投递链接 | 否 | 单个 HTTP/HTTPS URL |
| 投递渠道 | 否 | 可输入文本，如官网、内推、招聘平台 |
| 下次跟进日期 | 否 | 本地日历日期，可清空 |
| 通用备注 | 否 | 多行文本，第一版不要求富文本编辑器 |

### 4.2 阶段与结果必须分开

内置阶段及建议稳定 ID：

| ID | 展示名称 |
|---|---|
| `applied` | 已投递 |
| `screening` | 简历筛选中 |
| `assessment` | 笔试 / 测评 |
| `interview_1` | 一面 |
| `interview_2` | 二面 |
| `interview_3` | 三面 |
| `hr` | HR 面 |
| `offer` | Offer |

阶段顺序只用于展示，允许跳过、回退或直接进入任一阶段。不要强制每家公司走同一条流程。

`lifecycle` 建议为 `active` / `closed`；`outcome` 建议为 `rejected`、`offer_accepted`、`offer_declined`、`withdrawn`、`position_cancelled`、`other`。

核心规则：

1. 「流程结束」不是阶段。结束时保留当时阶段，例如「二面 · 已结束 · 未通过」。
2. 任意阶段都允许结束流程；接受或拒绝 Offer 的结果要求阶段为 Offer，UI 可引导用户先确认这一阶段变更。
3. 到达 Offer 不自动结束，用户仍可能在谈薪或等待决定。
4. 结束流程弹出表单，选择结果并填写可选原因；统一提交阶段、状态、结果、原因和时间线事件。
5. 已结束记录允许编辑信息或重新开启；重新开启时清空当前结束结果、原因与结束时间，旧内容保留在历史事件中。
6. 已结束记录的阶段调整属于更正，不自动重新开启；重新开启是明确操作。
7. 再次投递建议新建记录，与恢复原有流程区分。
8. `active` 记录没有当前结束结果或结束时间；`closed` 记录必须有有效结果和结束时间。后端校验这些不变量。

## 5. 流程时间线

自动记录创建、阶段变更、结束、重新开启；允许追加备注和补录历史阶段事件。普通文本字段的每次自动保存不生成时间线，避免输入时产生大量事件。

事件包含类型、前后阶段、结果/原因快照、备注、实际发生时间、记录时间。补录可以指定过去的日期；按实际发生时间展示，并用记录时间和 ID 稳定排序。

补录历史只增加事件，不自动覆盖当前状态。用户需要更改当前状态时执行明确的阶段修改、结束或重新开启操作。如此可避免补录一面记录把当前三面状态退回。

正常状态变更与对应事件必须在同一事务内提交。UI 的一次操作只产生一次逻辑事件，连续自动保存或失败重试不得重复记历史。

示例：

```text
11-03  创建投递：示例科技 / Go 后端工程师
11-05  简历筛选中 → 一面
11-08  一面 → 二面
11-10  流程结束：未通过（结束阶段：二面）
       原因：系统设计环节经验不足
```

## 6. 数据与架构建议

### 6.1 现有代码基础

- `backend/modules.go`：注册独立内置工具描述，目前不是动态插件运行时。
- `backend/app.go`：初始化业务服务及模块，提供全局删除、清空回收站入口。
- `frontend/sidebar.go`：已有多模块切换控件，但导航与页面内容仍主要面向项目。
- `frontend/workbench.go`、`frontend/workbench_load.go`、`frontend/task_save.go`：提供工作台、后台加载与草稿保存的参考实现。
- `backend/store/store.go`：共享数据库和一致性锁，当前 Schema 版本为 1，迁移方式需扩展为逐版本升级。
- `backend/backup/backup.go`：严格校验备份的 Schema 版本与数据库结构，不能只新增表而不处理恢复兼容。

### 6.2 服务与表

建议新增 `backend/jobapplications/`，由服务管理本模块的数据校验、查询、状态转换、历史和回收站。不要把投递映射为现有三状态任务。

建议使用两张表：

```text
job_applications
  id, company_name, position_name, applied_date
  stage, lifecycle, outcome, closure_reason, closed_at
  application_url, channel, next_follow_up_date, notes
  created_at, updated_at, deleted_at

job_application_events
  id, application_id, event_type
  from_stage, to_stage, outcome, reason, note
  occurred_at, created_at
```

表名与类型可按仓库规范调整。事件引用投递记录，软删除保留事件，彻底删除时级联清理。按常用筛选和排序字段设计索引，不为每个字段无差别建索引。

持久化字段使用稳定 ID，显示中文由 UI 映射。日期字段保存日历日期，创建、更新及事件时间使用明确的时间戳约定。结束记录与事件保存原因快照，之后重新开启不抹去历史原因。

### 6.3 共用能力的边界

- 工作台负责模块路由与全局设置，求职模块持有自己的页面与草稿状态。
- 原生系统能力通过 `frontend.Host` 调用，方便测试替身隔离。
- 共享 `Store` 与全量备份，渲染只读取 UI 缓存，不在渲染函数内获取数据库锁。
- 回收站列表聚合不同模块；删除、恢复和彻底删除按条目类型分发，不能全部交给项目服务。
- 第一版没有求职附件，避免提前泛化当前依赖任务 ID 的附件模型。

## 7. 自动保存与并发

参照现有任务草稿机制实现以下行为：

- 用户输入先进入本地草稿，后台串行持久化；连续输入合并为最新待保存版本。
- 显示正在保存、已保存、校验失败或保存失败，失败保留草稿并可重试。
- 快速切换记录、模块或页面时，旧加载结果不能覆盖新页面或新输入。
- 待保存时延后执行最后一次导航请求；保存失败不静默丢弃草稿。
- 丢弃修改、关闭详情、退出应用和恢复备份应具有与现有任务一致的保护语义。
- 行内编辑与详情编辑不能通过旧快照覆盖同一记录的新修改。
- 数据库长期占锁时仍可输入和渲染，等待只发生在后台任务。
- 重试流程操作避免重复事件；阶段变化、结束结果和时间线保持事务一致性。

## 8. 升级、备份与删除

数据库升级必须支持已有项目数据：按版本执行增量迁移，不能重新执行旧的建表语句。升级失败应回滚，不破坏原有数据。

全量导出必须包含投递记录与历史。新版本恢复旧版本合法备份时，应在隔离的暂存数据库完成版本对应的结构校验和迁移，再校验升级后结构，最后按现有安全备份与替换流程恢复。不能为了兼容而取消结构校验。拒绝未知的未来版本，旧版本应用也不能错误打开新数据库。

全量恢复是替换整个工作区：恢复不含求职数据的旧备份后，求职记录为空；恢复前安全备份保留恢复前的数据。应在恢复说明中明确这一语义。

回收站恢复必须带回完整历史；彻底删除才删除记录和事件。全局清空回收站覆盖两种模块，同时保留项目附件 GC 部分成功时的原有处理方式。

备份锁顺序始终为 `Store.BackupOperation` 在前、`Store.Exclusive` 在后。

## 9. 开发顺序

1. 增量迁移与独立业务服务：创建、查询、校验、状态变更、历史、软删除。
2. 模块导航与基础表格：确保项目与求职都能正常路由，含折叠侧栏。
3. 新增与详情、行内编辑、自动保存、搜索筛选排序和统计。
4. 时间线、补录、结束与重新开启流程。
5. 全局回收站分发、备份导出及旧备份恢复兼容。
6. 回归测试、视觉检查、文档同步和提交。

可以分阶段提交，但只有完成备份、回收站与并发保存验证后才算第一版可交付。执行时遵守根目录 `AGENTS.md`，不要将本方案中的建议命名当作必须建立复杂抽象的要求。

## 10. 验收与测试

### 10.1 用户行为验收

- 新建记录、重启应用后，字段和历史均保留。
- 同公司多岗位、同岗位再次投递均可保存，重复提醒不阻断合法创建。
- 可跳过轮次，二面结束后仍能看到结束阶段与失败原因。
- Offer 可继续推进，接受/拒绝后可结束；重新开启不丢失原结束历史。
- 补录旧事件不改变当前阶段；普通备注自动保存不制造流程事件。
- 筛选、搜索、排序返回正确记录；总数与匹配数口径明确，已删除记录不计入统计。
- 删除后可恢复完整记录与历史；彻底删除后不可恢复。
- 全量备份与恢复涵盖求职数据；合法旧备份可升级恢复，损坏或未知版本备份不替换现有数据。
- 切换模块、快速编辑和数据库繁忙不会导致草稿丢失、旧数据回填或 UI 阻塞。

### 10.2 测试要求

遵循根目录 `AGENTS.md`，重点覆盖可回归行为：

- 后端字段与状态不变量、事务原子性、重试去重、历史补录和删除级联。
- 旧数据库迁移、迁移失败保护、新旧备份恢复、损坏备份与未来版本拒绝。
- 使用 `openTestWorkbench` 与 `ui.Tester` 模拟新增、输入、阶段修改、筛选、导航、恢复和系统链接打开；断言数据库或工作台状态。
- 使用 `Host` 替身隔离系统能力和真实数据目录。
- 通过通道持有 `Store`，覆盖连续编辑、过期加载、保存失败、丢弃、切换模块、关闭和恢复保护；后台任务与 UI 回调分别排空，不使用固定睡眠。
- 检查原项目模块行为、回收站及附件 GC 未被破坏。
- 为求职表格和详情增加视觉快照覆盖，检查长公司名、长岗位名、长备注、空列表和窄窗口。
- 新 UI 测试运行 `-count=5`，提交前运行 `go test ./...`，完成适用静态检查。
- 修改本地 Lobe MyGo 副本时，额外运行其测试与 vet，并更新 `README.Aion.md`。

实现涉及的 README 功能、数据布局、开发流程与仓库结构说明应同步更新；如测试约定发生变化，同步更新 `AGENTS.md`。按仓库要求使用 Conventional Commits 提交，准备发布时更新 `CHANGELOG.md`。
