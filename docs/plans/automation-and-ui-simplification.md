# 开发自动化与 UI 封装精简方案

日期：2026-11-16  
状态：待实施；本文仅描述计划，Automation 尚未接入。  
顺序：先接入开发用 Automation，再分批清理 UI 封装中未使用的能力。

## 1. 目标与范围

为真实窗口调试、截图和操作验收提供统一入口，同时减少 Aion 自维护的 UI 分支和配置项。以保持现有用户行为、数据安全和视觉风格为前提，采用小步修改、独立验证、独立提交的方式实施。

本轮包含：

- 接入 MyGo Automation，仅在显式启用的开发测试构建中使用。
- 建立使用临时数据的真实窗口冒烟验收流程。
- 盘点 UI 封装的实际调用，删除确认没有业务用途的变体、参数和辅助代码。
- 同步开发文档与测试约定。

本轮不包含：SQLite 驱动迁移、MyGo 版本升级、SF Symbols 或其他新插件、界面改版、备份格式调整、数据迁移。日期选择器和 Toast 全面替换为官方默认控件也不在本轮范围内；需要改变现有外观或交互的替换另行评估。

## 2. 当前基础

- MyGo 锁定版本为 `v0.8.4-0.20261108082913-9233663736ca`，已包含 Automation；无需为了接入升级依赖。
- 更新功能已使用官方 `updater/native`，文件对话框、打开链接和 Finder 定位已使用 MyGo 核心 API。
- UI 测试通过 `openTestWorkbench`、`ui.Tester` 和可替换的 `frontend.Host` 隔离系统能力，并有无头快照入口。
- `frontend/ui_*.go` 在本次盘点时合计 4,942 行，其中包含应用风格、必要交互及较通用的可选能力。行数不是冗余量，也不作为必须删除的目标。
- `uiProgress` 的两个业务调用位于 `projects_view.go` 和 `task_detail_view.go`，目前均使用小尺寸普通横条和百分比文本，是第一批精简候选。

## 3. 第一阶段：接入开发用 Automation

### 3.1 接入方式

新增根目录文件 `automation_e2e.go`，仅做带构建标签的包导入：

```go
//go:build e2e

package main

import _ "github.com/egoist/mygo/plugins/automation"
```

不修改正常启动路径，不在 `main.go` 中无条件导入，不新增用户命令行参数。继续使用插件提供的 `MYGO_AUTOMATION` 环境变量指定 Unix socket。

保留两层构建隔离：

1. 普通构建不设置 `e2e`，因此不引入 Automation。
2. 官方发布构建默认使用 `mygo_noinspector`，插件在该配置下不启动服务。发布流程继续保持现有配置，不开启 Inspector。

### 3.2 开发运行方式

以下是接入完成后才能使用的示例，在仓库根目录执行。二进制、socket、数据和截图全部写入独立临时目录：

```sh
aion_e2e_dir=$(mktemp -d /tmp/aion-e2e.XXXXXX)
go build -tags e2e -o "$aion_e2e_dir/Aion" .
MYGO_AUTOMATION="$aion_e2e_dir/app.sock" \
  "$aion_e2e_dir/Aion" -data-dir "$aion_e2e_dir/data"
```

应用运行期间，在另一个终端把 `aion_e2e_dir` 设置为上一步输出文件所在的实际目录，再使用客户端：

```sh
# 在 Aion 模块目录中安装，以使用项目锁定的 MyGo 版本；无需 @latest。
go install github.com/egoist/mygo/plugins/automation/cmd/mygo-automation

mygo-automation open --socket "$aion_e2e_dir/app.sock"
mygo-automation snapshot -i
mygo-automation screenshot "$aion_e2e_dir/window.png"
mygo-automation close
```

客户端需在 PATH 中。`close` 结束客户端会话，应用仍需正常退出；退出后再清理本次创建的临时目录。若后续加入启动脚本，脚本应记录自己启动的进程，等待 socket 就绪，并只清理自身拥有的资源。

### 3.3 定位、等待与测试边界

- 优先使用现有辅助功能标签和稳定的 `Key`；仅对真实验收确实需要的控件补充 Key。不要把动态节点 ID 或本次快照的 `@eN` 编号固化到脚本。
- `idle` 表示窗口当前待绘制帧已处理，不代表数据库写入、后台工作或未来定时回调完成；持续动画也可能导致它超时。
- 等待操作结果时使用带截止时间的状态检查；失败时输出元素快照和截图，不使用固定睡眠作为正确性保证。
- `ui.Tester` 仍负责输入效果、异步保存、导航和锁竞争回归。`WaitForTasks` 后仍须单独排空 UI 回调。
- Automation 用于补充真实窗口验收，不替换既有确定性测试，也不通过它重做框架自身测试。
- 冒烟流程避开真实文件选择器、外部浏览器和真实用户数据；这些调用的业务行为继续通过 `Host` 桩验证。

### 3.4 最小冒烟场景

| 场景 | 操作与验收结果 |
| --- | --- |
| 项目与任务 | 创建项目和任务，修改详情，保存完成后重新打开，内容仍然存在 |
| 求职投递 | 新建投递并修改阶段，重新进入详情，记录和时间线符合操作结果 |
| 导航与快捷键 | 用菜单或快捷键进入设置、触发搜索，确认操作到达预期页面或输入框 |
| 关闭与重启 | 保存完成后正常退出，再用同一临时数据目录启动，确认数据保留 |
| 窗口检查 | 检查正常和窄窗口中的裁切、遮挡、焦点及可操作性，并保存截图 |

长持锁、保存失败、丢弃草稿、关闭保护等复杂场景继续由现有测试及必要的回归测试覆盖。读取数据库验收时优先在应用退出后进行，不绕过 Store 对活跃数据做写操作。

### 3.5 阶段验收

- `e2e` 构建配合环境变量可以连接、读取元素和执行输入；未指定 socket 时不监听。
- 普通构建不包含 Automation 依赖；设置环境变量也不会意外开启服务。
- `e2e,mygo_noinspector` 组合可以构建，并验证不会启动 Automation 服务。
- 使用独立临时数据完成最小冒烟场景；正常退出后 socket 被清理。
- README 记录可运行命令，AGENTS 记录 Automation 与 `ui.Tester` 的职责边界。
- 首期作为本地开发验收入口；在确认 macOS 图形会话条件前，不把真实窗口测试加入无条件 CI 门禁。

## 4. 第二阶段：清理 UI 封装中未使用的能力

### 4.1 先建立使用清单

逐项记录“定义、生产调用、测试用途、实际参数取值、拟删除内容、保留行为”。使用 `rg` 搜索定义和引用，再沿着包装函数、函数值、回调和枚举传递核对调用链。

不能仅凭某个字段没有显式赋值就删除它：Go 的零值、默认分支和间接调用也属于实际用途。只被测试使用的能力要先判断其保护的用户行为是否仍存在，再决定去留。

### 4.2 清理顺序

| 批次 | 文件与候选 | 处理方式 |
| --- | --- | --- |
| P1：进度条 | `ui_feedback.go` 的圆环、分段、Inset、状态及自定义参数 | 复核全部调用后删除未用分支及专属类型、辅助函数；保留横条、百分比、平滑变化和辅助功能数值 |
| P2：Markdown | `ui_markdown.go` 的流式揭示、聊天样式及附加配置 | 逐项确认未被使用后裁剪；保留当前 Markdown 预览、代码高亮、复制、折叠和主题适配 |
| P3：其他通用封装 | `ui_controls.go`、`ui_fields.go`、`ui_display.go`、`ui_layout.go`、`ui_overlay.go` | 只清理已经证明无用途的函数、变体、参数及专属资源，不趁机统一改写全部控件 |
| P4：主题与图标尾项 | `ui_theme.go`、`icons.go` | 在前面批次完成后清理失去全部引用的令牌、图标和缓存项，保留品牌及项目图标映射 |

P2、P3、P4 是审计候选，不预先断言其中每项都可删除。审计确认没有冗余时，该项直接结束，无需为了减少行数改写工作正常的代码。

### 4.3 保留的关键约束

- 日期选择器保留日期清空、禁用规则、月份/年份切换以及弹层对齐行为。
- Toast 保留动作按钮、关闭、暂停计时和当前视觉交互；已有框架底层能力继续复用。
- Markdown 保留原始文本持久化和当前代码块功能，不改用新的存储格式。
- 附件预览的解码限制、缓存边界、方向校正和过期结果保护属于业务保障，不作为通用 UI 冗余删除。
- 自动保存、草稿排序、导航保护、Store 锁顺序、备份和附件 GC 不属于本轮重构范围。
- 不以少写代码为由牺牲长持锁时的输入和渲染响应。

### 4.4 每批验证

1. 修改前记录相关行为和视觉基线，修改后检查相应页面截图。
2. 对实际可能回归的行为补测试；不为删除的未用变体补测试，不断言标签文案、默认值、行顺序或框架内部实现。
3. 新 UI 测试使用 `openTestWorkbench`、`ui.Tester` 和 `Host` 桩，运行 `-count=5`；新增测试以一句行为说明开头。
4. 每次提交前运行 `go test ./...`；实现批次另运行 `go vet ./...` 和 `go tool mygo vet .`。
5. 用 `TestVisualSnapshotRender` 检查看板、设置、求职列表、窄视图及详情弹窗；截图输出到临时目录。非发版不更新 README 发布截图。
6. 通过 Automation 检查本批涉及的真实窗口行为。若仅删除不可达代码，冒烟范围可聚焦相关页面。

## 5. 提交与文档安排

建议按以下边界独立提交，便于审阅和回退：

1. `test(e2e): add opt-in MyGo automation support`：开发入口、最小验收流程及开发文档。
2. `refactor(ui): remove unused progress variants`：进度条精简及必要回归验证。
3. `refactor(ui): trim unused markdown options`：仅在使用清单确认后实施。
4. 后续按控件族分别提交，描述实际删掉的能力，不使用笼统的“大规模 UI 重构”。

每批保持工作树可构建、测试通过。README 的开发流程和目录树、AGENTS 的测试规则，以及相关注释随实际变更同步；实施完成后更新本文状态和验收记录。准备发版时再更新 CHANGELOG 和发布截图。

若某批出现行为或视觉回归，修复或回退该批，不把未解决的问题带入下一批。UI 清理没有数据格式变更，因此回退不需要数据迁移。

## 6. 完成标准与收益评估

- [ ] 开发人员能按文档启动隔离实例，并通过 Automation 操作和截图。
- [ ] 默认构建和发布构建保持原有运行方式，不开启自动化服务。
- [ ] 每个删除项都有明确的无业务调用依据，必要行为和视觉保持一致。
- [ ] 原有测试及新增必要测试通过，新 UI 测试重复运行稳定。
- [ ] 记录删掉的变体、参数、辅助函数和净代码量；不以测试删减换取数字。
- [ ] 如衡量体积，使用同一架构、Go/MyGo 版本和发布参数比较，开发插件不计入正式包。

主要收益是降低维护和验收成本，不承诺显著缩小安装包。未引用函数可能已经被 Go 链接器移除；删除它们仍可减少阅读、修改和审查负担。
